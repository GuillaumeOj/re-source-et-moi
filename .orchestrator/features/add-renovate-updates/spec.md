# Add Renovate Updates — spec

## Goal

The GitHub repo is already connected to the Renovate app. Add the config file so Renovate
opens dependency-update PRs **once a week**, grouped so the week's work is a handful of PRs
instead of one per package:

- one PR for the **backend** (Python, `backend/pyproject.toml` + `backend/uv.lock`, uv);
- one PR for the **frontend** (`frontend/package.json` + `frontend/bun.lock`, bun);
- one PR for **lockfile maintenance** (refresh transitive deps in `uv.lock` and `bun.lock`).

No application code changes. Only one file is added: `renovate.json` at the repo root.

## What the repo looks like today (drives the config)

- Every direct dependency is pinned to an exact version (`django==6.0.6`, `"next": "16.2.9"`).
  Renovate must keep them exact pins (bump `X==a.b.c` → `X==a.b.d`, never widen to ranges).
- Backend: uv project (`pyproject.toml` `[project]` + `[dependency-groups] dev`, `uv.lock`),
  Python pinned to 3.13 in `.python-version`, `Dockerfile` (`python:3.13-slim`), CI
  (`setup-uv` `python-version: "3.13"`), and ruff/ty targets.
- Frontend: bun (`bun.lock`, text lockfile; CI runs `bun install --frozen-lockfile`).
- Other version sources Renovate will detect: `.github/workflows/ci.yml` (actions +
  `postgres:16` service), `docker-compose*.yml` (`postgres:16`), `frontend/Dockerfile`
  (`oven/bun:1.3.3-alpine`).
- CI has two drift guards: `schema.yml` regenerated by **drf-spectacular** and
  `lib/api/generated.ts` regenerated by **openapi-typescript**. A bump of either tool can
  change the generated output, which fails CI until someone regenerates and commits. The
  hosted Renovate app cannot run post-upgrade commands, so those PRs need a human.

## Behaviour

| Rule | Decision |
|---|---|
| Base preset | `config:recommended` (dependency dashboard issue, sane defaults). |
| Schedule | Weekly: `before 6am on monday`, timezone `Europe/Paris`. Applies to every update **and** lockfile maintenance. |
| Pinning | `rangeStrategy: "pin"` — keep the existing exact pins. |
| Backend group | All non-major updates of packages in `backend/**` (uv / pep621 manager) → one PR "backend dependencies". |
| Frontend group | All non-major updates of packages in `frontend/**` (bun / npm manager) → one PR "frontend dependencies". |
| Lockfile maintenance | Enabled, weekly, single PR covering `uv.lock` and `bun.lock`. |
| Major updates | **Not grouped**: one PR per major (Next 16→17, Django 6→7…) so a breaking upgrade never blocks the week's routine bumps. |
| Codegen tools | `drf-spectacular` and `openapi-typescript` get their own PR (outside the groups) since they may need a schema/types regen; the groups stay green and mergeable. |
| Python runtime | Not bumped by Renovate (Docker `python` image, `.python-version`). Moving Python 3.13→3.14 touches `.python-version`, `requires-python`, the Dockerfile, CI and the ruff/ty targets together — a deliberate manual change. |
| GitHub Actions & Docker images | Non-major updates grouped into one weekly "CI & Docker images" PR (actions, `oven/bun`, `postgres`). Majors (e.g. `postgres` 16→17, which must match the production DB) stay separate. |
| PR limits | `prHourlyLimit: 0` so the weekly batch opens in one run; `prConcurrentLimit` left at the preset default. |
| Labels | `dependencies`. |
| Automerge | Off — every PR is reviewed and merged by hand. |

## Acceptance

1. `renovate.json` exists at the repo root and passes `renovate-config-validator`
   (`npx --yes --package renovate -- renovate-config-validator`, or `bunx`).
2. The config expresses every row of the table above; each `packageRules` entry has a short
   `description` saying why it exists.
3. `README.md` gets a short "Dependency updates" paragraph: weekly schedule, the groups, and
   that drf-spectacular / openapi-typescript PRs need `uv run tox -e openapi` +
   `bun run codegen` before merge.
4. Existing CI is untouched and stays green (no code change).

## Out of scope

- Automerge, Renovate self-hosting, post-upgrade tasks.
- Adding a CI job that validates the Renovate config.
- Any dependency upgrade itself — Renovate will open those PRs after merge.

## Team / docs

Single small task, owned by `back` (repo-level tooling config); `front` reviews it since half
the rules target the frontend. No UI, no API: no `ux-brief.md` / `api-contract.md`.
